How I take an idea to the field

The loop I run for every new use case
STEP 1

Listen

I sit with site managers and safety teams and ask what keeps them up at night. Then I write it down as something a camera can actually check.

STEP 2

Sketch the site

Which cameras, how big an edge box, how much bandwidth, which firewall rules, and what takes over if something fails.

STEP 3

Build it

Detection, tracking, zones and dwell timers, composed into a workflow that fires on the right moment and stays quiet otherwise.

STEP 4

Teach the model

Fine-tune on footage from that site. Dust, glare and night shifts are where models fall apart, so that's where I spend my time.

STEP 5

Ship to the edge

Commission the box, plug in the streams, push the quantized model out, and make sure it survives a dropped link.

STEP 6

Prove it

Walk the site with the HSE team, trigger real scenarios on live cameras, watch the alert land where it should, sign off.

The longer version

  • Every new use case starts with me and a site or HQ safety team agreeing what "unsafe" looks like on camera, how we'll know the detector works, and who gets told when it fires.

Jun 2022 → Nov 2024 Pune, India Chapter 02

Storage, then automation

Rakuten Symphony (Robin.io) · Associate Software Engineer · mostly C, Python, Kubernetes and PostgreSQL

Fresh out of college I landed in a team building an S3-compatible object store from scratch to replace MinIO. I got to design the garbage collector, the part that quietly cleans up after deletes without ever losing data, even when a node dies halfway. Later I moved to MDCAP, the automation engine behind Rakuten's telco deployments, and touched everything from the workflow language to access control to how the containers were built.

  • Designed the distributed garbage collector: a transactional delete queue in PostgreSQL, at-least-once dispatch, and a multithreaded disk scanner that reconciles chunks against metadata and survives crashes.
  • Wrote four S3 APIs to the AWS spec, including zero-copy CopyObject using hardlinks and ranged GETs over O_DIRECT reads, all on Reed-Solomon 4+2 erasure coding.
  • Took the core image from 1.78 GB to 180 MB with a multi-stage build and single-file binaries, which closed a customer security escalation.
  • Extended the workflow language with loops and task grouping, then used it to write a 55-step resumable migration off Cisco VIM.
  • Built least-privilege access control with permission bitmaps in JWT claims, enforced per HTTP verb across 20+ resource types for 1,000+ clients.
The longer version

The object store

  • I packaged the whole thing into a one-command Kubernetes install: Helm charts with automatic rollback, disk-discovery DaemonSets, and three synchronously replicated Patroni PostgreSQL clusters.
  • I owned licensing: RSA-4096 keys issued from a Flask service, Evaluation, Production and Community tiers, capacity caps up to 1 PiB, expiry checks.
  • I built cross-site configuration sync for multi-cluster replication, with durable work queues and bounded retries so a crashed database or an unreachable peer didn't leave things half-done.
  • I wrote and ran the failure drills: killed pods and nodes, filled filesystems, partitioned the network, forced Patroni failover, and checked S3 kept answering.

MDCAP

  • Core features of a cloud-native automation platform (async Python on Sanic, PostgreSQL, Kubernetes) that runs declarative DAG workflows on containerized workers for Day-0 to Day-2 operations.
  • I made the fleet dashboard fast at scale by replacing dozens of count queries with one PL/pgSQL aggregation that uses planner estimates past 10,000 rows, refreshed every five minutes.
  • I built secure browser access to servers and BMCs: Wetty behind an Nginx WebSocket proxy, short-lived per-session tokens, power control through ipmitool.
  • I added Amazon EKS as a managed resource type alongside on-prem clusters, with IAM auth and lifecycle workflows.
